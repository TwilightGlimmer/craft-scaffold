# CraftScaffold 工程实践与决策记录

更新于2026-10-07。用途：保留项目怎么走到今天的证据与决策，供后续课程展示选材。本文不是最终实验报告，不预设新版课程会成功。

## 1. 项目故事的主线

**我们尝试让资源受限的 DreamerV3 智能体学会 Crafter 的长链条工具任务；实践发现，帮助智能体接触任务只是第一步，还必须保证场景、奖励、经验池、评测和运行系统彼此一致。**

最初问题是“给一点初始资源，能否提高学习效率”。随后问题变成：
1. 提升的是某一个动作，还是完整游戏能力？
2. 在准备好的场景中会做，能否从自然出生完成？
3. 辅助覆盖的技能是否过窄，退出辅助是否过早？
4. 修改任务后继续训练，旧经验是否仍对应当前目标？
5. 一次得分上涨或下跌，究竟来自学习、评测波动，还是工程故障？

这些问题逐步推动我们从单一木镐辅助，转向八技能、单回合单目标、并列前置课程与从零训练。当前最确定的成果是实验链路和可审计实现；新版性能收益仍待数据验证。

## 2. 决策过程：问题、证据、调整与边界

| 阶段 | 遇到的问题与思考 | 采取的办法 | 目前能说什么 |
|---|---|---|---|
| 早期导航方案 | 简化任务中 baseline 很强，感知预算机制是否有实际价值存疑 | 探索更长任务链、已有开源环境的游戏RL方向，最终采用 DreamerV3＋Crafter | 属于项目选题演变，不把早期导航成绩混入Crafter实验 |
| 旧3×3实验 | 自然、固定辅助、撤除辅助；辅助主要是工作台与一个木头 | 三种策略各训练11、23、41三个种子，观察300k结果 | 多种子用于看训练变异，种子不是单张地图编号 |
| 指标纠偏 | 早期分析过度关注木镐，甚至把单项下降概括为项目负结果 | 用户指出问题后补齐22项成就和标准Crafter Score，重新看全局 | **早期全局判断不完整，需要明确纠正。** 历史三种子汇总曾显示辅助全局正向；不能用单木镐或失败种子否定这一证据 |
| 区分局部技能与自然迁移 | 准备好的环境中能制作，不等于自然出生能收集材料并到达制作条件 | 使用自然场景与辅助场景分开诊断；检查前置条件、合法动作与策略历史 | 诊断可以支持某些解释，不能单靠最终模型差就断言“从未学会”或“发生遗忘” |
| 从方法比较转为工程选优 | 用户希望优先得到一个好用模型，而非持续扩充种子平均 | 从各旧策略中选表现好的候选继续到350k、400k，记录全部候选包括退步 | 这是开发集选优迭代，不能当作无偏的算法平均比较 |
| 曲线而非端点 | 400k端点退步不能告诉我们是持续退化还是中途波动 | 补评310–390k中间节点，使用同一评测协议并导出CSV | 10k分辨率只能定位变化区间，不能证明瞬时“崩塌”或具体学习原因 |
| 回退方案讨论 | 提出长期低于峰值或严重下降时从best重新分支 | 讨论后暂不实施，先解决辅助策略本身的问题 | 回退不是当前训练机制；不得在展示中画成已完成模块 |
| 多技能设计 | 工作台＋木头主要帮助木镐，对后续采石、煤、熔炉和铁链条覆盖不足 | 把木镐至钻石展开成八技能；煤炭、熔炉纳入课程 | 覆盖更完整是设计改进，不自动意味着Score更高 |
| 单目标与依赖关系 | 曾讨论窗口2同时学习；还存在并列依赖和顺序门槛问题 | 最终选择每回合单目标；采石/煤炭并列，石镐/熔炉并列；逐级整层半量移交 | 不声称已证明单目标优于窗口2；这是控制复杂度的选择 |
| 辅助状态审查 | 库存、工具、成就历史不一致可能导致重复前置动作、消耗材料，或产生伪成功 | 用原生准备动作建立前置；目标未解锁；前置已解锁且不再发奖；熔炉固定4石头＋可采石区域 | 环境单测通过不等于策略已能识别所有隐含进度 |
| 奖励与经验池 | 屏蔽非主线奖金后，旧经验仍携带旧奖励；只在辅助过滤还会让训练奖励规则随出生类型变化 | v5统一自然与辅助训练奖励；两组从零初始化、清空经验；不继续旧奖励经验池 | 消除了这类新旧目标混杂风险；没有证明它就是旧性能差的唯一原因 |
| 当前三路 | 两路新课程从零，旧自然baseline继续扩展 | seed23：同批0→400k、逐级0→400k、自然400k→800k，各占一GPU | 新课程训练奖励与旧自然baseline不同、总训练量也不同；需在同预算节点比较，不能把800k对400k当公平算法结论 |

旧探针、方案讨论和正式实验是不同层级的证据。没有原始汇总可复核的诊断不填具体效果数字；部分历史材料已归档，需从运行证据索引追溯后再用于展示。

## 3. 工程故障记录：不要误判为算法失败

### E01：关闭日志仍发生昂贵计算
- 现象：旧 fading_mix seed23 在285572步附近连续五次停滞。
- 定位：trace未开启，但调用参数中的指纹计算仍提前执行，涉及device读取与同步。
- 修复：在指纹计算外加显式trace条件；不改学习规则，单独版本化。
- 验证要求：旧版/修复版400步对比，修复版300＋2＋98恢复对比，正式checkpoint短续训。
- 边界：该修订去除了明确的额外工作；记录本身不支持“已完整证明所有JAX停滞原因”。

### E02：恢复训练不是只加载网络权重
- 需要恢复：优化器、经验池及采样状态、训练carry、环境与策略运行状态、计数器、随机数状态。
- 办法：连续训练与分段恢复做精确比较；物理执行动作和最终保留步数分开记账。
- 取舍：每10k完成保存，异常可能重做当前段；重做不能从成本统计中消失。
- 当前证据：两路fresh预检分别400对300＋100通过，初始agent也相同。
- 边界：短程精确恢复不等于长期性能稳定，更不等于课程一定有效。

### E03：NumPy全局随机状态遗漏
- 现象：旧multiskill预检中模型参数、优化器和计数一致，但numpy_rng不一致，正式训练被阻止。
- 修复：初始化前显式设置NumPy种子；完整恢复时仍由checkpoint覆盖。
- 教训：一个seed配置项不会自动覆盖所有库与随机源。训练种子与评测世界种子需分开记录。

### E04：预检空队列被误判为任务完成
- 现象：预检写入成功标记后返回空队列，调度器提前宣告完成，正式交互为零。
- 修复：要求明确进入训练阶段，并独立核验目标checkpoint、开发评测和留出评测；归档无效完成文件。
- 教训：进程退出码和status里的completed都不足以证明实验完成，要验收实际产物。

### E05：GPU进程判断与多路调度
- 现象：容器与驱动PID命名空间差异曾造成占卡误判；并行交接也出现锁竞争。
- 办法：核对PID与创建时间；空卡才启动；记录GPU UUID；冲突只终止自己的任务，完整恢复、限次重试。
- 当前规则：每路2核、20GiB显存、16GiB进程树内存；基线与两辅助最多三路。
- 教训：工具SSH超时不等于远程训练失败，不应因此重复启动；程序存活也不等于有进展。

### E06：checkpoint堆积与结果可追溯
- 问题：全状态checkpoint体积大，频繁保存很快挤占空间；直接删除又会丢失曲线证据。
- 办法：先核验22项成就评测与模型哈希，持久化CSV，再清理。
- 保留：0、50k倍数、实测峰值、最新恢复点、待评测点及活跃/门槛依赖。
- 已完成的一次旧曲线清理：33个实测节点核验后，删除22个非关键目录，实际释放约51GiB（对应独立审计）。
- 后续一次清理：23目录逻辑体积约44.74GiB；逻辑大小不等于实测释放空间。未评测旧节点暂留。
- 教训：节省存储不能靠删掉失败结果或填补未经测量的分数。

### E07：本地监控成本
- 问题：持续等待和反复检查浪费交互与token。
- 办法：长任务由远程管理器运行，本地30分钟唤醒一次；正常状态静默，故障/阶段完成再通知。
- 教训：训练调度与用户沟通监控分离，笔记本重启不应直接终止远程任务。

## 4. 当前方案及尚未解决的问题

当前策略详见[训练策略说明](current-training-strategy.md)。

- 同批：自然70%，八技能各3.75%，不按学习进展改变比例。
- 逐级：自然70%，辅助总30%；并列层级内均分，经过连续开发检查和独立确认后分两轮移交。钻石最终通过后归还自然训练。
- 辅助状态是构造的合法初始状态，没有专家动作标签；调度器使用任务信息，不宣称严格无监督。
- 所有训练回合统一主线成就奖金＋健康变化；自然评测保留原始奖励与全部22成就。
- 自然baseline延续原始奖励。**奖励改变是混杂因素**，后续若要分离课程贡献，需要同奖励自然对照；目前没有自动启动该额外实验。
- 相同seed只能控制初始化等部分随机条件，不保证不同课程后续轨迹相同。
- 20k双轮门槛较保守：六层完全退出的理论最快进程需要约480k；400k是阶段预算，不保证通关或课程全部毕业。
- 准备成本、训练交互、评测交互、预检和恢复开销都要披露。
- 单配对seed不能证明跨种子稳定提升，旧模型选优也不能证明找到了最优参数。

## 5. 后续PPT可以怎样讲

以下是叙事提纲，尚未制作PPT，不是最终结论。

| 叙事节点 | 讲清楚什么 | 应配证据/画面 |
|---|---|---|
| 1 场景与约束 | 无真实机器人，用开源游戏验证世界模型RL长链任务 | 游戏画面、工具依赖图、实际资源预算 |
| 2 第一版为什么合理 | 少量准备帮助探索稀疏的制作机会 | 自然与旧工作台/木头出生对照 |
| 3 第一轮判断为何不够 | 单木镐掩盖多任务收益与代价 | 22成就热图＋全局Score；明确纠正早期分析 |
| 4 为什么继续训练不总涨 | 端点、波动、选优偏差要分开看 | 同协议10k曲线，保留下降段 |
| 5 如何排除软件因素 | 恢复、随机源、调度器、GPU竞争 | 故障→修复→验收三列表，选2个重点 |
| 6 怎样重构辅助 | 从一个出生补丁到八技能依赖课程 | 前置状态表与并列层级移交图 |
| 7 为什么最终从零重训 | 奖励改版和旧经验存在一致性风险 | 旧/新transition奖励示例与空经验池起点 |
| 8 我们真正交付了什么 | 可运行、可恢复、可评测、可追溯的系统；性能按实测报告 | 三路曲线、独立留出结果、成本账本 |

不要把每次失败都包装成成功；展示一个错误判断如何被指标纠正、一个软件故障如何被一致性检查抓住，比罗列大量版本名更有说服力。
最终若性能没有提升，可以讲清“哪些工程问题已排除，哪些学习问题尚未解决”，不能把验证工具的成功当作算法收益。

## 6. 后续每轮更新模板

每次重要变更追加一条，不覆盖旧解释：
- **问题/触发数据**：具体模型、checkpoint、评测协议及观察。
- **候选解释**：至少区分实现问题、统计波动、训练目标和任务迁移。
- **最小验证**：不改变哪些条件，改变哪个因素，预算与验收门槛。
- **结果**：包括失败、超时和未完成，附原始证据索引。
- **决定**：采用/放弃/暂缓，并说明理由。
- **证据边界**：已证实事实、合理推测、仍未验证的部分。
- **成本**：有效动作、额外物理动作、GPU时间、存储与人工排错。
